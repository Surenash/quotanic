# Decision History Log

**Decision 1:** Use Django for the backend and React/Vite for the frontend within the same repository (`manfacquot`).
- **Context:** Need a robust backend for complex FBM calculations and database management, but also require a modern, reactive frontend for the user interface.
- **Reason:** Django provides excellent ORM and admin capabilities, while React offers a better user experience for dynamic forms (like CAD uploads and configuration).
- **Alternatives:** Separate repos for front and back end, using Django templates (too slow for the desired UX), or using a Node.js backend.

**Decision 2:** Use Celery and Redis for asynchronous task processing.
- **Context:** Processing CAD files and generating quotes via the FBM engine is computationally expensive and slow.
- **Reason:** Doing this synchronously in the Django request/response cycle would lead to timeouts and poor UX. Celery allows for robust background processing.

**Decision 3:** Direct-to-S3 Uploads for CAD Files.
- **Context:** CAD files can be large and uploading them through the Django server consumes unnecessary bandwidth and blocks worker threads.
- **Reason:** Using pre-signed URLs generated by Django allows the frontend to upload directly to an S3 bucket (`quotanic-fbm-designs-mumbai`), keeping the backend performant.

**Decision 4:** Deploy PostgreSQL via Docker on EC2 instead of AWS RDS.
- **Context:** Encountered silent failures across multiple attempts when trying to create an AWS RDS instance for the database.
- **Reason:** To ensure project progress, the database was moved into a Docker container (`ubuntu-db-1`) alongside the Django app on the EC2 `t3.micro` instance, with a volume mount for persistence.
